# 第 12 讲：Token 额度的预留与结算

这是单进程、单计量维度的教学示例。它控制预估用量的准入，并演示编号、幂等、欠额和用量未知的处理；不实现厂商限流、Redis、多层级协调、在途并发或费用预算。

## 运行

在专栏根目录执行，Python 3.9 及以上、仅需标准库：

```bash
python3 12-配套代码/demo.py
python3 -m unittest discover -s 12-配套代码 -v
```

演示使用固定时钟，输出保存于 `demo_output.txt`；直接运行 `token_limiter.py` 也会执行同一演示。22 项测试覆盖超大请求、足额准入、预留重放、重复结算、冲突用量、欠额、未知用量、迟到退款、配置与输入校验、记录上限、线程并发以及 `Retry-After` 取整。

正文代码片段可在 `12-配套代码` 目录运行。它用预设最终量代替真实上游调用，仅验证额度变化，不调用模型。

## 计量与时间假设

- 输入、输出、缓存等如何折算为计量额度，由调用方定义。预估量、部分用量与最终量必须属于同一维度、同一目标范围。
- 预留编号对应一次上游尝试，由服务端生成并绑定请求。重试和并行尝试各自申请，不能因业务请求相同而漏计其真实消耗。本示例只校验同一编号的估计值一致，没有存储完整请求指纹、租户或目标信息。
- 补充速率为 `tokens_per_minute / 60`，容量为该速率乘以 `burst_seconds`。容量与每分钟速率分别控制突发和长期补充。
- 预留时必须足额。估计量大于容量返回 `oversized`；额度暂时不足返回 `limited`，等待量为 `(estimate - level) / rate`。等待建议不预占未来额度，竞争请求可能使它失效。
- 结算补扣可导致负余额，后续请求要等到足以支付其完整估计量。原有调用已经消耗的资源不能通过补扣撤销。
- 默认使用单调时钟。测试时钟不得倒退；非有限值与非法 Token 数不参与额度计算。

## 预留生命周期

| 操作或状态 | 行为 |
| --- | --- |
| 新编号足额预留 | 返回 `reserved`，只有这个返回值的 `allowed` 为 true |
| 同一编号再次申请 | 返回 `replayed`，不重新扣减，不许可再次派发；估计值不同则报错 |
| 最终量齐全 | `settle(id, actual_tokens)` 处理差额并记录 `final` |
| 相同最终量再次结算 | 返回已存结果，`replayed=True`，没有新的扣退；返回的金额字段是原回执，不能再应用一次 |
| 最终量冲突 | 报错，不改动余额；本示例不提供人工账务修正协议 |
| 调用结束但缺最终量 | `mark_unknown(id, observed_tokens)` 记录 `unknown`；不根据部分用量退款，已知量超预留则补扣 |
| 未知后取得最终量 | `settle` 从暂记量核对到实报量；不得低于此前已确认的部分值 |
| 未知量通知重放 | 同一部分值无副作用；不同值报冲突。此方法用于调用结束时一次性登记，不是流内进度更新接口 |

`observed_tokens` 必须是已确认、同口径的累计部分量；它不是从可见文本猜出的最终用量。没有可靠部分值时可省略，默认零表示“没有已确认的部分”，而 `actual_tokens` 仍为 `None`，不是把实际量断言为零。

用量状态与传输状态分别管理。本例不负责释放在途槽位，也不会因一个未知用量记录而永久冻结速率补充。对累计费用预算，必须单独设计预留与核对逻辑。

## 迟到退款：保守的速率额度释放

不能把费用差额直接加入当前速率桶。例如：

1. 容量 10000、每秒补充 1000；时刻 0 为旧请求预扣 8000。
2. 时刻 8，桶已补满；新请求预扣 10000，余额变为 0。
3. 时刻 8.1，旧请求报告实际用量 1000。
4. 如果此时机械退回 7000，刚接受过一个满桶请求的系统就又取得一大块突发额度。

本例为每次扣减保留“尚未被补充恢复”的数量；时间补充按扣减顺序抵消，退款最多释放本次预留仍未恢复的部分。上述例子退款为 0，余额约为 100；最终实报量仍记录为 1000。

这种分配是保守的，不保证等于按真实用量重放全部历史后的最优可用额度，也不是厂商算法。它避免重复释放已经恢复的额度，不承诺实际生成量满足严格滑动窗口上限。补扣按收到结算的时间影响当前准入；如果需要把消耗严格归属到生成时间，需另行设计事件时间、窗口与迟到更新规则。

退款未必等于 `estimate - actual`，但实报用量始终完整保存。费用账本应核对完整金额差异，不复用本例的 `credited_tokens` 当作费用退款。

## 已知限制

- 线程锁只保护同一进程。同一桶的状态、记录、补扣与退款需要一起持久化和恢复，才能扩展到进程崩溃或多实例环境；不能只共享一个余额。
- 默认最多保留 10000 条已接受的记录，终态记录也计入。达到上限返回 `record_limit`，不伪装成暂时 Token 不足，也不提供虚假的 `Retry-After`。这是有界演示，不是常驻服务的记录生命周期方案。
- 未实现自动删除或 TTL。删除幂等记录后旧请求可能再次到达，生产系统需要明确保留期、过期编号和恢复策略；不能随意清空状态重新获得满桶。
- 预留记录与扣减队列占用内存，补充可能遍历多条扣减，不代表已优化的高吞吐实现。本轮不提供性能基准。
- 未实现有界透支、多层级事务、配额租约、Redis 故障降级、生成中累计用量更新或实际取消。
- 估计准确也不保证实际生成时刻符合上游 OTPM；应结合上游反馈、输出上限与并发约束。

`render_figures.mjs` 输出三张可编辑 SVG 和 300 dpi PNG，默认宽度 150 mm、最小字号约 9.1 pt。依赖 Node.js、`sharp`、`@napi-rs/canvas` 和中文字体，默认 Hiragino Sans GB。

node 12-配套代码/render_figures.mjs /tmp/llmgw-ch12-preview
